## 2. 문제와 목표

회의록, 업무보고, 공문 등 여러 형식의 문서는 분량이 길고 핵심 내용과 확인 항목이 흩어져 있어 검토 시간이 오래 걸린다. 사용자가 문서를 업로드하면 시스템은 문서에서 텍스트를 추출하고, 핵심 내용을 요약하며, 사전에 정한 검증 항목의 확인 결과를 제공한다.

MVP의 목표는 **단일 문서를 업로드해 요약 결과와 검증 결과를 조회할 수 있는 흐름**을 완성하는 것이다.

## 3. 대상 사용자와 사용 시나리오

| 사용자 | 필요 | 대표 시나리오 |
| --- | --- | --- |
| 문서 작성·검토 담당자 | 긴 문서의 빠른 파악 | 회의록을 올리고 결정 사항·담당자·기한을 확인한다. |
| 업무 관리자 | 누락된 업무 요소 확인 | 업무보고에서 담당자, 일정, 요청 사항의 언급 여부를 확인한다. |

기본 흐름은 다음과 같다.

1. 사용자가 지원 형식의 문서를 한 개 업로드한다.
2. 시스템이 텍스트를 추출하고 분석한다.
3. 사용자가 원문 요약과 검증 결과를 화면 또는 API 응답으로 확인한다.
4. 실패 시 시스템은 실패 원인과 재시도 방법을 안내한다.

## 4. 범위와 가정

### 4.1 MVP 포함 범위

- PDF, DOCX, TXT, HWPX, PPTX 파일 한 개의 업로드 및 텍스트 추출
- 추출된 텍스트의 핵심 내용 요약
- 문서 유형별 기본 검증 항목에 대한 결과 제공
- 처리 실패·미지원 형식·빈 문서에 대한 오류 응답
- FastAPI 기반 API 제공

### 4.2 가정

- 초기 MVP는 인증 없이 제한된 내부 사용자를 대상으로 한다.
- 데이터베이스는 사용하지 않으며, 분석 결과의 장기 보관·검색은 범위에서 제외한다.
- 검증은 문서 내용의 존재 여부와 명확성에 대한 AI의 보조 판단이며, 법률·행정적 사실의 최종 판정이 아니다.
- HWP(v5 바이너리) 파일은 지원하지 않는다. HWPX로 변환한 파일만 처리한다.
- 세부 UI는 추후 결정하며, MVP의 우선 산출물은 API와 응답 구조다.

### 4.3 범위 제외

- 사용자 로그인·권한 관리
- 다중 문서 비교, 문서 간 질의, 장기 이력 관리
- 원본 문서의 수정·재저장
- OCR이 필요한 스캔 이미지 중심 문서 처리
- 법적 효력을 갖는 자동 결재·감사 판정

## 5. 기능 요구사항

| ID | 요구사항 | 입력 | 처리 | 출력 / 완료 기준 |
| --- | --- | --- | --- |
| FR-01 | 문서 업로드 | 지원 확장자의 파일 1개 | 파일 존재 여부, 크기, 확장자를 검사한다. | 분석 요청이 생성되며 잘못된 요청은 이유와 함께 거절된다. |
| FR-02 | 텍스트 추출 | 업로드된 PDF, DOCX, TXT, HWPX, PPTX | 형식별 파서로 읽을 수 있는 텍스트를 추출한다. | 추출 텍스트 또는 추출 실패 사유를 반환한다. |
| FR-03 | 문서 유형 식별 | 추출 텍스트와 사용자가 선택한 유형(선택) | 회의록, 업무보고, 공문 중 분석 기준을 결정한다. 사용자가 지정하면 이를 우선한다. | 적용한 문서 유형을 결과에 포함한다. |
| FR-04 | 핵심 요약 | 추출 텍스트 | 제목/목적, 핵심 내용, 결정·요청 사항, 담당자·기한 정보를 가능한 범위에서 구조화해 요약한다. | 사람이 빠르게 읽을 수 있는 요약과 항목별 결과를 반환한다. |
| FR-05 | 필수 항목 검증 | 추출 텍스트, 문서 유형 | 유형별 기본 검증 항목의 언급·누락·판단불가 여부와 근거를 분석한다. | 항목별 상태, 근거 문장 또는 판단 사유를 반환한다. |
| FR-06 | 오류 처리 | 손상 파일, 빈 파일, 미지원 형식, 추출 실패 | 오류를 분류하고 민감한 원문을 로그/응답에 노출하지 않는다. | 사용자에게 이해 가능한 오류 코드·메시지·다음 행동을 반환한다. |

### 5.1 기본 검증 항목

| 문서 유형 | 검증 항목 |
| --- | --- |
| 회의록 | 회의 일시, 참석자, 안건, 결정 사항, 담당자, 기한 |
| 업무보고 | 보고 대상/기간, 주요 진행 내용, 이슈·위험, 요청 또는 다음 계획 |
| 공문 | 수신처, 발신처, 제목/목적, 시행 또는 작성일, 요청·협조 사항 |

검증 상태는 `확인됨`, `누락 가능성`, `판단 불가` 중 하나로 표현한다. AI가 확신할 수 없는 경우에는 `확인됨`으로 단정하지 않는다.

## 6. 데이터 입·출력 요구사항

### 6.1 분석 요청 입력

- `file`: 분석할 파일 1개, 필수
- `document_type`: `meeting_minutes`, `work_report`, `official_document` 중 선택, 선택 입력
- `summary_length`: `short`, `medium` 중 선택, 기본값은 `medium`

허용 확장자는 `.pdf`, `.docx`, `.txt`, `.hwpx`, `.pptx`이다. 최대 파일 크기와 허용 MIME 타입은 구현 전에 팀 공통 설정으로 확정한다.

### 6.2 분석 결과 출력

```json
{
  "document_type": "meeting_minutes",
  "summary": {
    "overview": "문서의 핵심 내용",
    "key_points": ["핵심 항목"],
    "action_items": [{"task": "후속 업무", "owner": "담당자 또는 미확인", "due_date": "기한 또는 미확인"}]
  },
  "validation_results": [
    {"item": "결정 사항", "status": "확인됨", "evidence": "근거 요약"}
  ],
  "warnings": []
}
```

이 구조는 초안이다. 실제 구현 시 팀의 공통 API 모델이 이미 있으면 그 모델을 우선한다.

## 7. 비기능 요구사항

| ID | 요구사항 |
| --- | --- |
| NFR-01 | API는 JSON 응답을 제공하고, 입력 검증 오류와 서버 오류를 구분한 HTTP 상태 코드를 사용한다. |
| NFR-02 | API 키, 토큰, 업로드 원문, 개인정보를 응답 또는 일반 로그에 그대로 기록하지 않는다. |
| NFR-03 | 업로드 파일은 분석에 필요한 기간만 임시 보관하고, 처리 후 정리 정책을 구현 전에 정한다. |
| NFR-04 | 지원하지 않는 형식과 텍스트를 추출할 수 없는 파일은 시스템 중단 없이 처리한다. |
| NFR-05 | 동일 입력에서 결과 구조와 검증 상태 값은 일관된 형식을 유지한다. |
| NFR-06 | HWPX 처리에는 `python-hwpx`를 사용하며, 원본 파일을 덮어쓰지 않는다. |

## 8. 수용 기준

다음 조건을 만족하면 MVP 요구사항을 충족한 것으로 판단한다.

1. 지원 형식의 비민감 테스트 문서 각각에서 업로드부터 결과 응답까지 동작한다.
2. 정상 문서 응답에 문서 유형, 요약, 검증 결과가 모두 포함된다.
3. 회의록 테스트 문서에서 결정 사항·담당자·기한의 확인 결과를 반환한다.
4. 빈 파일, 미지원 확장자, 손상 파일에 대해 서버 오류 없이 명확한 오류 응답을 반환한다.
5. 오류 응답과 로그에 원문 전체나 인증 정보가 포함되지 않는다.
6. HWPX 테스트 시 원본을 변경하지 않고, 텍스트 추출 또는 명확한 실패 사유를 제공한다.

## 9. 미결 사항

- 업로드 최대 크기와 파일 보관 기간
- AI 모델, 프롬프트, 호출 비용 한도
- 문서 유형 자동 식별의 신뢰도 기준과 사용자 수정 방식
- 검증 결과의 근거 문장 표시 범위
- UI 제공 시점과 화면 구성

위 미결 사항은 구현 시작 전 팀 합의가 필요하며, 합의 전에는 보수적인 기본값과 명시적 오류 처리를 적용한다.
